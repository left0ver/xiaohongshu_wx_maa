# 视频号第一批采集

更新时间：2026-11-05。当前完成手机端流程接入，服务端上报暂缓，尚未通过稳定性验收。

本次审阅修订：采集优先使用实时控件树，稳定导航回退至模板，均不满足时才调用 OCR；控件和导航模板点击前重新核对目标。组合点赞已撤销固定坐标三连点，恢复识别白色拇指后单击并验证红色状态。基础信息新增 5 秒就绪重试窗口。修订后采集流程已完成三轮真机测试，1 轮成功、2 轮失败，导航耗时明显增加，尚未通过验收。

## 采集范围

- 启动微信，进入发现 → 视频号 → 推荐页。启动前台切换和页面就绪共用最长 10 秒重试窗口；同步 OCR 调用本身不被该窗口强制中断。
- 导航先在屏幕下方 1/4 识别「发现」，点击后在上方 1/4 识别「视频号」及推荐标签。Maa 底层仍获取整帧，ROI 仅限制 OCR 范围。
- 读取作者昵称、完整视频文案、发布时间原文和地点。兼容昵称与「作者」标签同一行或分行；文案在「音乐」边界结束。
- 进入作者主页和更多信息，读取认证、简介、IP 归属地、资料所在地及真实视频号 ID。打开「更多信息」时启动 5 秒就绪重试窗口，包含点击后的固定等待；识别到基础信息和有效视频号 ID 就立即继续，未就绪时最多间隔 0.5 秒再检查，超时停止且不保存。不重复点击菜单；同步 OCR 本身无法中断，因此该步骤实际耗时仍可能超过 5 秒。未显示字段保留 null，不推测补齐。
- 返回原视频，严格校验作者和文案；文案不一致时重新识别一次，仍不一致就停止且不保存。
- 按规范化作者名和完整文案生成去重键，本地重复采集保留事件 ID、设备 ID 和首次采集时间。

`videoUrl` 是 `wechat-channels://video/<hash>` 本地标识，不是真实分享 URL。时间保留页面原文，不补造年份。当前结果为 `local_only`，没有授权码上报、ACK 或远端 SQL 验收。

## 使用和代码位置

按根 README 构建微信 APK。手机解锁、亮屏、竖屏，启动 Shizuku 并授权助手，开启前台模式。在任务页仅选择「采集当前视频（第一批）」；关闭运行前强制停止和运行后关闭目标应用，运行中不要切换到其他应用。它会从微信入口进入推荐流，并非保证沿用启动前正在观看的作品。

- `plugins/wechat/wechat_channels/collector/collection.py`：解析、导航、身份校验、SQLite 保存和计时。
- `collector/android_ui.py`：控件树、模板、OCR 与点击适配；包含独立手机验收适配器。
- `collector/hierarchy.py`：过滤微信可见控件、坐标转换、字段完整性与点击前唯一性/位置校验。控件树不完整会回退，不将部分文字当作完整采集结果。
- `collector/commands.py`：复用小红书的 Android `posix_spawn` 命令执行方案，包含子进程超时和取消；Java 导出源码复用小红书插件，微信只调用通用 XML 导出功能。
- `collector/main.py`：应用内 Agent 入口；`phone.py` 和 `run-phone.sh` 是独立手机开发入口，需要另行部署 runtime 和 PI，不能当作应用内性能测试。
- `resource/base/pipeline/collect-video.json`：采集入口、OCR 与作者更多信息模板节点。
- `collector/test_collection.py`：采集纯业务测试，含基础信息就绪等待的成功、超时及不保存分支；`collector/acceptance.sql`：本地数据库只读验收查询。

应用内数据目录由 profile 的 `WECHAT_DATA_DIR` 设置，当前为 `/data/local/tmp/wechat-channels-data`。其中 `videos.sqlite3` 保存本地草稿，`runs/<runId>/` 保存 OCR 证据、`timings.jsonl` 和成功结果。数据、截图、运行日志、runtime ZIP、APK 和签名密钥不提交仓库。

识别证据新增 `source` 和 `attempts`；应用日志的 `recognitionTiming` 记录每次控件树、模板和 OCR 尝试耗时，可验证 OCR 是否实际被跳过。控件树未暴露的字段仍依赖 OCR，旧昵称、文案和去重限制尚不能视为全部解决。

## 修订后三轮应用内实测（2026-11-05）

发现的问题：

- 第 1 轮基础信息未通过校验。该次识别用时 10.366 秒（控件树 0.981 秒、OCR 9.385 秒），只读到视频字幕和状态栏；任务结束截图中基础信息面板已经出现。说明至少存在页面采样时机问题，尚不能只归因于 OCR 准确率。同步 OCR 已超过 5 秒就绪窗口，未能启动第二次检查；当前实现不是整个步骤的 5 秒硬超时。
- 第 2 轮文案下方为「原声」，OCR 输出「」原声」，现有文案边界只兼容「音乐」等形式，未接受该行；当次截图尚未读到评论时间作为备用边界，因此报 `The full description boundary is not visible`。没有保存不完整文案。
- 第 3 轮完整成功，返回作者和文案校验通过。SQLite 中结果与该轮 `video.json` 一致，状态为 `local_only`，认证字段未显示而保留缺失；重复去重键及无效草稿查询均为 0。前两轮没有 `video.json`，也未进入保存阶段。

25 次页面快照最终采用 OCR 22 次、模板 3 次、控件树 0 次。三次模板成功都发生在「视频号」入口；「发现」和「推荐」仍回退 OCR。快照中累计尝试耗时：控件树 27.852 秒、模板 153.224 秒、OCR 346.289 秒；这些统计不包括点击前模板重新确认和独立的作者菜单模板调用，不能视为完整耗时拆分。三轮结束后单独导出控件树，helper 正常退出，但结果为 `<hierarchy />`；该补查不计入三轮耗时。

导航平均 113.474 秒，旧版三轮平均 55.232 秒；本次约为旧版的 2.05 倍。仅导航快照中的模板尝试每轮平均 51.075 秒，还存在模板点击前二次识别开销，因此目前没有实现预期提速。下一步应优先排查控件树空结果、模板匹配耗时及重复识别，再处理基础信息采样和「原声」边界兼容。

本地证据在 `plugins/wechat/data/acceptance/semantic-three-app-runs/`（被 Git 忽略）：`summary.json`、`database-check.json`、包内源码校验记录，以及各轮识别 JSON、应用日志、阶段日志和结束截图。采集 runId 分别为 `b434b3cd-bd0d-4acb-a55d-fff8f3ea68f5`、`8484dca7-4c93-41c8-a470-4c7482d0aedf`、`cf5cd34a-d16d-4b8a-98b3-7a2ff274dce1`。
