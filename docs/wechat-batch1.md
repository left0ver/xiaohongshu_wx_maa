## 采集范围

2026-11-05 后续简介修订：简介以完整统计行或功能区作为结束边界，取消对正文中「粉丝」等词的宽泛过滤；对简介区域补做 OCR，过滤彩色装饰，允许省略装饰表情。应用内使用 `Context.run_recognition`，避免向正在执行的任务队列再次提交导致等待；控件树前台确认超时回退 OCR，后续 OCR 仍检查前台。

连续一轮三个不同视频的简介专项核对通过，耗时 20.192 / 12.581 / 11.540 秒，其中一例展开简介；这些是直接手机执行的专项耗时，不是应用内整条采集耗时。随后应用内完整采集回归通过，耗时 234.065 秒，简介与截图一致。证据位于本地 `data/acceptance/bio-strategy-5/` 和 `bio-strategy-5-app/`。此前策略失败均不计入通过轮次：表情误识别为 0、嵌套任务识别停滞、含「粉丝」的正文被删、控件树确认超时。视频文案曾另行复现混入评论，仍待修复，不能以简介通过代替第一批整体验收。

第二批已开始：`collector/comments.py` 解析当前屏幕完整可见的一级评论，保留原始时间/地区，保存本地 `COMMENT` 草稿并关联已存在的 `VIDEO.event_id`；按作品、昵称、正文、时间、地区去重。新增可选任务「采集作品及可见评论（第二批开发中）」，默认不勾选。真机独立专项读取并保存 2 条评论，耗时 12.693 秒，保存 0.011 秒；昵称仍有 OCR 错字和徽章混入，属于开发中的字段质量问题。全量翻页、二级回复展开及关联、评论者视频号 ID 回填、上报/ACK 均未完成，结果显式标记 `coverage=visible_first_level_only`、`complete=false`。不能把该初版标为第二批验收通过。证据位于 `data/acceptance/comments-preview/`。

- 启动微信，进入发现 → 视频号 → 推荐页。启动前台切换和页面就绪共用最长 10 秒重试窗口；同步 OCR 调用本身不被该窗口强制中断。
- 导航先在屏幕下方 1/4 识别「发现」，点击后在上方 1/4 识别「视频号」及推荐标签。Maa 底层仍获取整帧，ROI 仅限制 OCR 范围。
- 读取作者昵称、完整视频文案、发布时间原文和地点。根据行高和相邻关系组合昵称、「作者」、地点及时间，兼容同一行、独立文本框、上下分行和时间/地点顺序变化。「音乐 / 原声」需满足控制行结构；评论边界需同时具备作者、地区、时间及右侧计数，单独日期或正文关键词不作为边界。作者头部被滚出时，只在已确认的评论抽屉内向下恢复一次；作品文案最多展开两次，无法确认完整边界则停止。
- 进入作者主页和更多信息，读取认证、简介、IP 归属地、资料所在地及真实视频号 ID。字段按标签与值配对，支持同行、下行及换行。认证与所在地不混入简介；简介折叠时最多展开一次，仍被截断就保留 null 并记录缺失。
- 基础信息识别进程在点击前准备，耗时单独记录。点击「更多信息」起共享 5 秒就绪预算，包含点击及固定等待；优先控件树，再匹配「基础信息 + 视频号 ID」模板，失败才用区域 OCR。模板以 360 像素短边识别，先试基准尺寸，再试其他尺寸。预算耗尽即终止并回收只读子进程，不重复点击菜单；进程回收可能产生几十毫秒尾部开销。就绪仅表示面板出现，有效 ID 等字段的读取与校验另计，尚未取得有效 ID 时不能保存。这个预算不等于整个作者资料任务只需 5 秒。
- 作者资料读取结束后返回视频页面，直接保存本轮首次采集结果；不执行 `verify_original_video` / `verify_description_retry`，日志中不再出现这两个耗时阶段。必要的页面定位、文案完整边界和有效 ID 检查保留。
- 按规范化作者名和完整文案生成去重键，本地重复采集保留事件 ID、设备 ID 和首次采集时间。

`videoUrl` 是 `wechat-channels://video/<hash>` 本地标识，不是真实分享 URL。时间保留页面原文，不补造年份。当前结果为 `local_only`，没有授权码上报、ACK 或远端 SQL 验收。

## 使用和代码位置

按根 README 构建微信 APK。手机解锁、亮屏、竖屏，启动 Shizuku 并授权助手，开启前台模式。在任务页仅选择「采集当前视频（第一批）」；关闭运行前强制停止和运行后关闭目标应用，运行中不要切换到其他应用。它会从微信入口进入推荐流，并非保证沿用启动前正在观看的作品。

- `plugins/wechat/wechat_channels/collector/collection.py`：解析、导航、首次结果保留、SQLite 保存和计时。
- `collector/android_ui.py`：控件树、模板、OCR 与点击适配；包含独立手机验收适配器。
- `collector/hierarchy.py`：过滤微信可见控件、坐标转换、字段完整性与点击前唯一性/位置校验。控件树不完整会回退，不将部分文字当作完整采集结果。
- `collector/layout.py`：相对行高、作品区域、元数据、评论边界及标签/值关联；区域 OCR 替换旧区域观测，避免重复拼接。
- `collector/readiness.py`、`probe_reader.py`、`probe.py`：共享就绪预算、子进程准备/取消/回收与独立只读模板/OCR。
- `collector/commands.py`：复用小红书的 Android `posix_spawn` 命令执行方案，包含子进程超时和取消；Java 导出源码复用小红书插件，微信只调用通用 XML 导出功能。
- `collector/main.py`：应用内 Agent 入口；`phone.py` 和 `run-phone.sh` 是独立手机开发入口，需要另行部署 runtime 和 PI，不能当作应用内性能测试。
- `resource/base/pipeline/collect-video.json`：采集入口、OCR 与作者更多信息模板节点。
- `collector/test_collection.py`：采集纯业务测试，含基础信息就绪等待的成功、超时及不保存分支；`collector/acceptance.sql`：本地数据库只读验收查询。

应用内数据目录由 profile 的 `WECHAT_DATA_DIR` 设置，当前为 `/data/local/tmp/wechat-channels-data`。其中 `videos.sqlite3` 保存本地草稿，`runs/<runId>/` 保存 OCR 证据、`timings.jsonl` 和成功结果。数据、截图、运行日志、runtime ZIP、APK 和签名密钥不提交仓库。

识别证据记录 `source`、`attempts` 及逐字段 `fields`，包含原值、状态、来源、文本框、观测编号和时间。`observed` 只表示当前快照读到值，不代表已进行跨页面身份核对；`not_observed` / `truncated` 表示缺失或折叠。应用日志的 `recognitionTiming` 记录每次控件树、模板和 OCR 尝试耗时；`readinessPreparationTiming` 与 `readinessTiming` 分别记录准备和就绪检测，任务总时长包含这些开销。

本机修订后的 Java helper 正常运行，但微信仍返回 `rootPackage=com.tencent.mm rootClass=null rootChildren=0 exported=0`。已修复不可见父节点导致整个子树被丢弃的问题；系统实际没有提供节点时仍需模板/OCR。区域补读和混合来源通过合成数据测试，本机尚无法验证真实的部分控件树。模板样本来自浅色界面；其他机型、字体和深色界面仍需验证。未知地区不会凭昵称或正文猜测；去重仍基于昵称和文案，不是真实作品 ID。

- 第 2 轮文案下方为「原声」，OCR 输出「」原声」，现有文案边界只兼容「音乐」等形式，未接受该行；当次截图尚未读到评论时间作为备用边界，因此报 `The full description boundary is not visible`。没有保存不完整文案。
